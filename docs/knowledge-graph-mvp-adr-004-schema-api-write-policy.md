# ADR-004: MVP schema, tool contract, and reviewed-write policy

**Status:** accepted for MVP

**Date:** 2026-08-06

**Decision task:** KGM-1.4

## Context

The MVP needs enough structure to represent evidence-backed project knowledge without becoming an ontology platform. It must support exact/alias lookup, directed one-hop relationships, typed literals, minimal time, correction/supersession, and auditable proposals while keeping tool schemas and outputs small.

The extension must not treat an LLM assertion or confidence value as accepted truth. Agent-generated and user-directed writes therefore use one proposal/review path. The extension never calls a second model to extract facts during the MVP.

## Canonical records

SQLite is the canonical store. Names below are logical contracts; KGM-2.4/KGM-2.5 may choose table names without changing these semantics.

### Scope

A scope is either:

- `global`, intentionally visible across projects only when requested; or
- `project:<sha256>` as defined by ADR-003.

Every entity, alias, claim, evidence record, proposal, and audit event has one explicit scope. Scope is applied before lookup, ranking, expansion, or exact-ID access.

### Opaque stable IDs

IDs are generated by an injected ID factory and persisted unchanged. They are not SQLite rowids and do not encode labels or source content.

| Record | Format |
|---|---|
| entity | `ent_<UUID>` |
| alias | `als_<UUID>` |
| claim | `clm_<UUID>` |
| evidence | `evd_<UUID>` |
| proposal | `prp_<UUID>` |
| audit event | `aud_<UUID>` |

`<UUID>` is lowercase canonical UUID text. API validation accepts only the expected type prefix and UUID shape; callers cannot supply arbitrary table names, SQL, or internal rowids. Tests inject deterministic IDs, clocks, and hashes.

### Entity and alias

An entity contains:

- stable ID;
- scope;
- canonical display label, maximum 256 Unicode code points;
- normalized label for lookup;
- one closed MVP type enum: `person`, `project`, `repository`, `service`, `tool`, `organization`, `location`, `preference`, `concept`, or `other`;
- lifecycle status: `proposed`, `accepted`, or `rejected`;
- creation and review timestamps;
- proposal reference when created by a proposal.

An alias contains a stable ID, entity ID, scope, display alias, normalized alias, status, and proposal reference. Normalization applies Unicode NFKC, trimming, Unicode lower-casing, and internal whitespace collapsing while preserving the original display text. An accepted normalized alias is unique within a scope; ambiguous proposed matches remain explicit and are not silently merged.

Entity merge/split workflows are deferred. Accepting a second label never silently changes an existing entity’s identity.

### Evidence

Evidence is immutable after creation. It contains:

- stable ID and scope;
- source kind: `user_statement`, `pi_session`, `file`, `command`, `url`, or `other`;
- optional locator, maximum 2,048 code points;
- exact excerpt, maximum 4,000 Unicode code points at input;
- SHA-256 hash of the exact UTF-8 excerpt;
- server-generated capture timestamp;
- optional candidate source-observed timestamp;
- server-assigned trust class: `user`, `agent`, `local_file`, `local_command`, `external`, or `unknown`;
- Pi provenance when available: session ID, session entry ID, tool-call ID, branch leaf, and actor type.

`source kind` is descriptive input and never grants trust. An agent tool call cannot label its own evidence as user-trusted. User trust is assigned only by the user-originated review/command path. Secret scanning, size checks, and runtime validation happen before evidence persistence.

A claim-to-evidence relation identifies primary/supporting evidence. Correcting an excerpt creates new evidence; it never edits an existing excerpt.

### Claim

A claim is a directed assertion:

```text
subject entity -- predicate --> object
```

It contains:

- stable ID and scope;
- accepted/proposed/rejected/superseded status;
- subject entity ID;
- normalized predicate;
- typed object;
- server-generated `observed_at` timestamp for proposal receipt;
- optional `valid_from` and `valid_to` timestamps supplied as candidate facts;
- creation/review timestamps;
- optional replacement/supersession links;
- proposal reference when created by a proposal.

Predicates are normalized ASCII keys matching:

```text
^[a-z][a-z0-9_.-]{0,63}$
```

The MVP does not silently invent predicates, aliases, domain/range rules, or inverse relations. A predicate may be reviewed and accepted if it satisfies the syntax and policy; vocabulary governance is post-MVP.

Valid intervals use half-open semantics `[valid_from, valid_to)`. A missing start means unbounded before; a missing end means unbounded after. A supplied end must be later than the supplied start. Current retrieval uses the server’s `asOf` time and excludes claims outside the interval. `superseded` is an explicit correction/history state and is not inferred merely because a valid interval ended.

### Typed object

An object is exactly one of:

```json
{ "kind": "entity", "entityId": "ent_<UUID>" }
{ "kind": "text", "value": "..." }
{ "kind": "number", "value": 12.5 }
{ "kind": "boolean", "value": true }
{ "kind": "date", "value": "2026-08-06T00:00:00.000Z" }
{ "kind": "url", "value": "https://example.invalid/resource" }
```

Literal limits are 2,048 code points for text, 1,024 for URLs, and finite IEEE-754 numbers only. Dates must be UTC RFC 3339 timestamps. URL values are parsed and validated at the boundary. Arbitrary JSON, binary values, code, and unbounded text are not MVP object types.

### Proposal workflow

A proposal is a review workflow record, not accepted knowledge. It contains a stable ID, target scope, actor/provenance, idempotency key or normalized candidate fingerprint, status, creation/review timestamps, and references to proposed entities, aliases, claims, and evidence.

Proposal statuses are `pending`, `accepted`, `rejected`, and `cancelled`. Canonical candidate rows may exist with `proposed` status and remain invisible to accepted retrieval. A rejected proposal is retained for audit until explicitly purged.

A proposal contains exactly one candidate claim in the MVP, with zero, one, or two entity creations and up to eight aliases per created entity. Existing entity IDs may be referenced. This keeps review atomic and avoids bulk autonomous writes.

If normalized candidate content is already accepted, the service returns `already_known` with the existing claim ID and does not persist a duplicate proposal or new evidence. Evidence attachment to an existing accepted claim is deferred beyond the MVP. If an identical candidate is already pending, the service returns that pending proposal ID. It never creates a silent duplicate or silently changes the accepted claim.

### Supersession and correction

Correction is append-oriented:

1. retain the prior claim and evidence;
2. create a replacement claim and new evidence/proposal;
3. on user acceptance, link the replacement to the prior claim;
4. mark the prior claim `superseded` and exclude it from default current retrieval;
5. retain both in explicit history views.

No accepted claim is overwritten in place. A replacement may supersede only claims in the same scope and must record the reason through audit references/evidence.

### Audit event

Audit events are append-only and contain:

- stable ID;
- actor type: `user`, `agent`, or `system`;
- action: proposal creation/review, acceptance, rejection, correction, supersession, export, forget, purge, migration, or recovery;
- target type and stable ID;
- scope;
- server timestamp;
- Pi session ID, session entry ID, tool-call ID, and branch leaf when available;
- before/after stable-ID references and bounded redacted metadata.

Audit records do not duplicate full excerpts or arbitrary tool payloads. The canonical evidence/claim records are the source for content inspection.

## Tool contracts

All three tools use strict TypeBox schemas with `additionalProperties: false`, runtime validation of the received `unknown` value, normalized defaults, and bounded output. The exact TypeBox implementation belongs to KGM-4.2/KGM-4.3; these are the normative fields.

### `knowledge_search`

Parameters:

| Field | Contract |
|---|---|
| `query` | required non-empty string, maximum 512 Unicode code points |
| `limit` | optional integer `1..20`, default `8` |
| `includeGlobal` | optional boolean, default `false` |
| `includeHistory` | optional boolean, default `false` |
| `asOf` | optional UTC RFC 3339 timestamp, default server now |

Search always uses the current project scope. `includeGlobal: true` explicitly adds global scope; it never adds another project. Search filters scope and accepted/current status before ranking. History is opt-in.

Each result includes a result kind (`claim` or `entity`), stable ID, compact subject/predicate/object or entity label/type, matching fields, status/time summary, and up to three evidence citations. Evidence excerpts are truncated to 1,000 Unicode code points with an explicit truncation marker. Source content is labeled untrusted data.

The response includes `schemaVersion`, resolved visibility labels (`current_project`, optionally `global`), `results`, `truncated`, and `insufficientEvidence`. UTF-8 serialized output is capped at 12 KiB; results are removed deterministically from the end if needed. The response never includes raw SQL, arbitrary scope keys, or excluded-scope counts/content.

### `knowledge_get`

Parameters:

| Field | Contract |
|---|---|
| `id` | required stable `ent_`, `als_`, `clm_`, or `evd_` ID |
| `view` | optional enum `summary`, `history`, `neighbors`, or `evidence`; default `summary` |
| `limit` | optional integer `1..20`, default `8`; applies to history/neighbors/evidence |
| `direction` | optional enum `incoming`, `outgoing`, or `both`; only meaningful for `neighbors`, default `both` |
| `includeGlobal` | optional boolean, default `false` |

The ID must be visible in the current project scope or the explicitly requested global scope. An ID never bypasses visibility. `neighbors` is one hop only, cycle-safe, status-filtered, scope-filtered, and bounded. `history` includes supersession links and evidence without rewriting the current result. The response uses the same 12 KiB UTF-8 cap and citation limits as search.

### `knowledge_propose`

Parameters:

| Field | Contract |
|---|---|
| `scope` | optional enum `current_project` or `global`, default `current_project`; global requires explicit user review |
| `subject` | required entity reference: existing `entityId`, or new `label` + `type` + up to eight aliases |
| `predicate` | required normalized predicate key, maximum 64 characters |
| `object` | required typed object; entity objects may reference an existing ID or create one new entity |
| `validFrom` | optional UTC RFC 3339 timestamp |
| `validTo` | optional UTC RFC 3339 timestamp later than `validFrom` |
| `evidence` | required array of `1..5` entries with source kind, excerpt, optional locator, and optional source-observed timestamp |
| `idempotencyKey` | optional non-empty string, maximum 128 characters |

New entity labels and aliases use the entity limits above. Existing IDs must have the expected `ent_` prefix and are resolved only in the target visibility set. The tool does not accept `status`, `accepted`, `trust`, `actor`, `observedAt`, raw scope IDs, confidence, SQL, or arbitrary metadata from the model.

A successful agent call returns `pending`, a proposal ID, target visibility label, candidate summary, review-required flag, and no accepted claim. It may return `already_known` when an identical accepted fingerprint exists. It cannot accept, reject, correct, delete, or purge data.

## Write policy and mode behavior

### Common path

Agent tool calls and user-directed remember commands call the same normalized proposal service. The service:

1. validates the unknown input against the strict schema;
2. resolves scope and applies the explicit global policy;
3. normalizes labels, aliases, predicates, literals, and timestamps;
4. checks limits, duplicates, references, and idempotency;
5. scans all proposed excerpts/locators for secrets before persistence;
6. persists a pending proposal, candidate rows, evidence, and an audit event transactionally;
7. returns a proposal reference for review.

User-originated commands may provide actor provenance, but the model cannot self-assign user trust. Acceptance is a separate transaction that records the reviewing user and promotes proposed rows.

### TUI and RPC

`knowledge_propose` never blocks on a confirmation dialog during LLM tool execution. It creates a pending proposal and displays a concise review-required result. `/knowledge-review` lists only pending proposals in the current visibility set, shows candidate claims and evidence, and requires explicit confirmation before accept, reject, edit, or supersede. RPC clients use the same explicit review/confirmation contract when dialog UI is available.

### Print and JSON

Print and JSON modes may submit a pending proposal if policy and input validation permit, but they never wait for UI and never report a proposal as accepted. If a mode cannot persist safely, it returns a stable error and leaves no partial canonical mutation. Acceptance requires a later explicit review-capable invocation.

### Failure guarantees

Every mutation is transactional. Cancellation before commit leaves no partial accepted/candidate graph. Busy/locked storage errors are normalized to a bounded retry or stable error. Tool output errors use stable categories such as `invalid_input`, `scope_unavailable`, `not_found`, `busy`, `storage_unavailable`, `secret_detected`, `proposal_pending`, and `output_truncated`; raw SQL, filesystem, and secret values are not returned.

## Consequences

- The initial schema includes workflow/proposal state in addition to canonical graph rows, but accepted retrieval remains simple and status-filtered.
- One-claim proposals make review and audit understandable and keep transaction size bounded.
- The agent can remember explicit facts through `knowledge_propose`, but user review remains the authority for durable acceptance.
- The API is intentionally less expressive than SQL/graph query languages; richer queries are deferred until measured use requires them.
- A future automatic extractor must produce the same proposal payload and cannot bypass this policy.
